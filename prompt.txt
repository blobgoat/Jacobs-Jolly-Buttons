# Implementation Prompt: Palantir Custom Button Group Widget

## Objective

Replace the existing todo-list demonstration in `src/Widget.tsx` with a configurable button-group widget for Palantir Foundry Workshop.

The widget must allow Workshop authors to configure multiple buttons through `src/main.config.ts`. Each button can:

* Act as a momentary push button or a persistent switch.
* Emit its configured ID when hovered or pressed.
* Emit its new active state when toggled.
* Display a text label and optional icon or media asset.
* Use configurable colors, corner rounding, font size, padding, interactive spacing, shadows, and background imagery.
* Collapse to an icon-only button when the widget container becomes too narrow.
* Display its label in a black tooltip while collapsed.

The group must support:

* Joined buttons with no visible spacing.
* Buttons distributed evenly across the available width.
* A custom gap between buttons.
* Automatic responsive collapse.
* Manual icon-only collapse.

This is a single Foundry Workshop widget. Do not redesign the project into a general component library, introduce a separate application architecture, or create additional widget manifests.

# 5. Foundry Events

Declare exactly three widget events in `main.config.ts`.

## `buttonHovered`

Triggered when the pointer enters a non-disabled button.

It must update:

```text
lastButtonId
lastButtonInteraction
lastButtonActive
```

Values:

```ts
{
  lastButtonId: button.id,
  lastButtonInteraction: "hover",
  lastButtonActive: currentActiveState
}
```

Do not emit this event repeatedly while the pointer remains over the same button.

## `buttonPressed`

Triggered once when a non-disabled button completes a valid activation.

For pointer interaction, a valid activation requires:

1. Pointer press begins inside the button’s interactive region.
2. Pointer release occurs inside the same interactive region.

For keyboard interaction, Enter or Space should count as a valid activation.

It must update:

```text
lastButtonId
lastButtonInteraction
lastButtonActive
```

Values:

```ts
{
  lastButtonId: button.id,
  lastButtonInteraction: "press",
  lastButtonActive: currentActiveState
}
```

For a momentary button, this is its primary action event.

## `buttonChanged`

Triggered after a switch button changes between active and inactive.

It must update:

```text
lastButtonId
lastButtonInteraction
lastButtonActive
activeButtonIdsJson
```

Values:

```ts
{
  lastButtonId: button.id,
  lastButtonInteraction: "change",
  lastButtonActive: newActiveState,
  activeButtonIdsJson: JSON.stringify(updatedActiveButtonIds)
}
```

Do not declare a dynamic Foundry event for every button. Foundry event IDs must remain static.

The dynamic button ID belongs in the parameter updates.

# 7. JSON Validation

Create a small parsing and validation utility in `buttonWidget.utils.ts`.

Do not add a large validation framework solely for this feature unless the repository already includes one that is appropriate.

Validation requirements:

* `buttonsJson` must parse into an array.
* Each entry must be an object.
* Each entry must contain a non-empty string `id`.
* Each entry must contain a non-empty string `label`.
* IDs must be unique.
* Invalid entries should be skipped rather than crashing the entire widget.
* Unknown properties may be ignored.
* Invalid enum values should use defaults.
* Invalid numeric values should be clamped or replaced with defaults.
* Duplicate IDs should keep the first valid entry and skip later duplicates.
* Development warnings should identify invalid entries using `console.warn`.
* Do not include the raw entire configuration in warnings if it may be excessively large.

If every entry is invalid, render an informative Radix callout or text message:

```text
No valid buttons are configured.
```

Do not throw an uncaught error.

# 10. Individual Button DOM Structure

Use a native `<button type="button">`.

The button must have two conceptual layers:

```html
<button class="interactive-hit-area">
  <span class="visual-button-surface">
    <span class="button-content">
      ...
    </span>
  </span>
</button>
```

Actual class names are not required because styles may be inline.

Responsibilities:

## Interactive hit area

The native button owns:

* Pointer events.
* Keyboard events.
* Focus.
* Disabled semantics.
* Transparent interactive spacing.

The configured `interactiveMarginX` and `interactiveMarginY` should be implemented as transparent padding around the visual surface.

This means the transparent area must activate:

* Hover.
* Pressed state.
* Click/activation.
* Keyboard focus outline.

Do not use ordinary CSS margin for this feature because ordinary margins are not interactive.

## Visual surface

The inner surface owns:

* Background color or image.
* Border radius.
* Outer shadow.
* Inner shadow.
* Press translation.
* State colors.
* Visible dimensions.

Only the visual surface should move during the pressed animation.

The outer native button must remain stationary so the layout and hit target do not shift.

# 11. Button States

Each button must support:

```text
default
hovered
pressed
active
disabled
collapsed
```

`collapsed` controls content presentation and can coexist with the other states.

Use this visual-state priority:

```text
disabled
pressed
active + hovered
active
hovered
default
```

Examples:

* A disabled button never displays pressed styling.
* An active switch can still display hover feedback.
* A collapsed active button remains visibly active.
* Pressing an active switch temporarily displays pressed styling before resolving to the next active state.

---

# 12. Interaction Modes

## Momentary mode

For:

```ts
mode: "momentary"
```

Behavior:

1. Pointer or keyboard press begins.
2. Button enters the pressed visual state.
3. Valid release completes the activation.
4. `buttonPressed` is emitted.
5. Button returns to its default or hovered visual state.
6. The button does not remain active.

## Switch mode

For:

```ts
mode: "switch"
```

Behavior:

1. Pointer or keyboard press begins.
2. Button enters the pressed visual state.
3. Valid release toggles its active value.
4. `buttonPressed` is emitted.
5. `buttonChanged` is emitted with the new active value.
6. The button remains in its active style until toggled again.

Use:

```tsx
aria-pressed={active}
```

for switch buttons.

Do not use `aria-pressed` for momentary buttons.

---

# 13. Switch State and Foundry Synchronization

Parse `activeButtonIdsJson` as an array of string IDs.

For switch buttons:

* If `activeButtonIdsJson` is valid, treat it as the external active-state value.
* Otherwise, initialize from each button’s `defaultActive`.
* Maintain optimistic local state so the interaction appears immediate.
* After a toggle, emit the updated `activeButtonIdsJson`.
* When a new `activeButtonIdsJson` value arrives through `parameters.values`, reconcile local state to that value.

Momentary button IDs must not be stored in `activeButtonIdsJson`.

Unknown IDs in `activeButtonIdsJson` should be ignored.

# 14. Icon and Media Behavior

A button may display an icon or image using `iconSrc`.

Requirements:

* Render the asset using an `<img>`.
* Support left and right positions.
* Default to left.
* Set `pointerEvents: "none"` on the image.
* Preserve aspect ratio with `object-fit: contain`.
* Keep the icon vertically centered.
* Use a maximum icon size of approximately 60% of `buttonHeightPx`.
* Use `iconAlt` when supplied.
* If the visible label provides the accessible name, use an empty image alt value unless the image communicates additional information.
* Keep the configured icon visible when collapsed.

If an icon fails to load:

* Do not crash.
* Preserve the label.
* Do not automatically collapse that button.
* Log one development warning for that button ID.

---

# 15. Background Image Behavior

When `backgroundImageSrc` is supplied:

* Use it as the visual surface background.
* Apply `backgroundImageFit` through `background-size`.
* Center the image.
* Do not render a separate interactive image element.
* Keep the button label and icon above the background.
* Apply state colors as semi-transparent overlays or filters so hover, pressed, active, and disabled states remain distinguishable.
* Clip the background to the same border radius as the surface.

When no background image is supplied, use the configured state background color directly.

# 16. Corner Rounding

Calculate border radius from the actual configured button height:

```ts
borderRadiusPx =
  buttonHeightPx * clamp(roundingCoefficient, 0, 0.5);
```

Examples for a 40-pixel button:

```text
0.00 → 0px
0.10 → 4px
0.25 → 10px
0.50 → 20px
```

Use the same radius for:

* Surface background.
* Background image clipping.
* State overlay.
* Outer shape.
* Joined-group outer corners.

# 17. Shadow System

The shadow system must use one shared coefficient.

Use these base values.

## Resting shadow

```css
box-shadow:
  0 4px 8px rgba(0, 0, 0, 0.22),
  inset 0 1px 1px rgba(255, 255, 255, 0.18);
```

## Hover shadow

```css
box-shadow:
  0 5px 10px rgba(0, 0, 0, 0.24),
  inset 0 1px 1px rgba(255, 255, 255, 0.20);
```

## Pressed shadow

```css
box-shadow:
  0 1px 2px rgba(0, 0, 0, 0.18),
  inset 0 3px 6px rgba(0, 0, 0, 0.28);
```

Scale all numeric shadow measurements by:

```ts
shadowCoefficient
```

Example:

```ts
scaledOuterOffsetY = 4 * shadowCoefficient;
scaledOuterBlur = 8 * shadowCoefficient;
scaledInnerOffsetY = 1 * shadowCoefficient;
```

Pressed translation:

```ts
translateY = 2 * shadowCoefficient;
```

The visual surface must use:

```text
transform: translateY(...)
```

while pressed.

The native button hit area must not move.

Animate:

* Background color.

* Transform.

# 19. Button Group Layout Modes

Version one supports horizontal groups only.

Do not implement vertical groups in this task.

## Joined mode

For:

```text
layoutMode = joined
```

Requirements:

* Visual gap between surfaces is exactly `0px`.
* Inner horizontal border radii are removed.
* The first visible button retains its left corner radii.
* The last visible button retains its right corner radii.
* Middle buttons have `0px` horizontal radius.
* A one-button group retains its complete radius.
* Each button remains independently interactive.
* Pressing one button moves only that button’s visual surface.
* Internal interactive margins are forced to `0px` to prevent overlap and visible separation.
* Outer interactive margins may remain on the first and last button.

If borders are added during implementation, shared borders must not appear doubled.

## Space-between mode

For:

```text
layoutMode = space-between
```

Requirements:

* Group width is `100%`.
* First button aligns with the group start.
* Last button aligns with the group end.
* Remaining space is distributed evenly using the equivalent of:

```css
justify-content: space-between;
```

* Button widths remain content-based.
* Buttons retain their complete border radii.
* Configured interactive margins remain active.
* `customGapPx` is ignored.

For a group containing one button, align it at the start.

## Custom-gap mode

For:

```text
layoutMode = custom-gap
```

Requirements:

* Use `customGapPx` as the exact CSS flex gap between native button hit areas.
* Buttons retain their complete border radii.
* Configured interactive margins remain active.
* Clamp negative gaps to `0`.
* Include the gap when calculating responsive overflow.

# 20. Group Padding

Apply `groupPaddingPx` uniformly to the button-group container.

The padding:

* Is not associated with any particular button.
* Does not activate a button.
* Must be included in responsive width calculations.
* Must not clip tooltips or focus indicators.

# 21. Collapse Behavior

A button may collapse to icon-only presentation.

Collapse can be triggered by:

1. Global manual collapse:

```text
collapseMode = always
```

2. Automatic container overflow:

```text
collapseMode = auto
```

3. Per-button configuration:

```ts
collapseMode: "always"
```

A button with:

```ts
collapseMode: "never"
```

must not collapse automatically.

The global `collapseMode` has this behavior:

```text
always:
Collapse every button that has a working icon and is not configured as never.

auto:
Collapse eligible buttons only when needed.

never:
Do not perform group-level automatic collapse. Individual buttons configured
as always may still remain collapsed.
```

---

# 22. Collapsed Button Dimensions

A collapsed button must:

* Hide its visible text label.
* Remove the icon-label gap.
* Center its icon.
* Preserve the label for accessibility.
* Use a visual-surface width equal to `buttonHeightPx`.
* Use a visual-surface height equal to `buttonHeightPx`.

Therefore, an icon-only visual surface is objectively square:

```text
width / height = 1
```

The transparent interactive margins remain outside this square surface.

Do not collapse a button without a successfully loaded icon.

---

# 23. Automatic Responsive Collapse

Automatic collapse must use the widget’s actual container width, not `window.innerWidth`.

Use `ResizeObserver` on the group container.

The algorithm must be:

1. Measure the available content width of the group.
2. Determine the width required for all expanded buttons.
3. Include:

   * Group padding.
   * Flex gaps.
   * Interactive margins.
   * Button visual widths.
4. If the expanded group fits, render eligible buttons expanded.
5. If it does not fit, collapse eligible buttons according to the selected strategy.
6. Recalculate after every collapsed button.
7. Stop when:

   * The group fits, or
   * No additional eligible button can collapse.
8. If all eligible buttons are collapsed and the group still does not fit, enable horizontal scrolling.
9. Never clip or silently hide a button.
10. Restore labels when sufficient width becomes available.

Perform measurements through `requestAnimationFrame` after resize notifications to avoid excessive synchronous measurements.

Cancel an outstanding animation-frame callback when the component unmounts.

---

# 24. Collapse Strategies

## Priority strategy

For:

```text
collapseStrategy = priority
```

Use the following deterministic order:

1. Lower `collapsePriority` values collapse first.
2. When two buttons have the same priority, the button later in the array collapses first.
3. Buttons configured as `"never"` are excluded.
4. Buttons without a successfully loaded icon are excluded.
5. Buttons configured as `"always"` begin collapsed and do not participate in ordering.

Example:

```json
[
  {
    "id": "primary",
    "collapsePriority": 10
  },
  {
    "id": "secondary",
    "collapsePriority": 1
  },
  {
    "id": "tertiary",
    "collapsePriority": 1
  }
]
```

Collapse order:

```text
tertiary
secondary
primary
```

## All-at-once strategy

For:

```text
collapseStrategy = all-at-once
```

When the fully expanded group does not fit:

* Collapse every eligible auto-collapse button in one state update.
* Keep `"never"` buttons expanded.
* Keep buttons without icons expanded.
* Keep `"always"` buttons collapsed.

---

# 25. Collapse Hysteresis

Prevent rapid collapse/expand flickering.

Use:

```text
collapse buffer: 8px
expand buffer: 16px
```

Collapse when:

```ts
requiredWidth > availableWidth - 8
```

Restore an expanded label only when:

```ts
requiredExpandedWidth <= availableWidth - 16
```

This creates a stable difference between the collapse and expansion thresholds.

# 26. Tooltip Behavior

Every collapsed button must have a tooltip containing its complete label.

Use the installed Radix tooltip implementation where available.

Tooltip requirements:

* Tooltip content is the button’s `label`.
* Default background is black or at least 92% opaque black.
* Text is white.
* Default position is above the button.
* Delay is controlled by `tooltipDelayMs`.
* Tooltip appears on pointer hover.
* Tooltip appears on keyboard focus.
* Tooltip disappears on pointer leave.
* Tooltip disappears on blur.
* Tooltip disappears immediately when the button expands.
* Tooltip does not affect layout measurements.
* Tooltip must not intercept pointer events.
* Tooltip must not be clipped by the group container.
* Long labels may wrap.
* Maximum tooltip width is 240 pixels.

Suggested appearance:

```ts
{
  backgroundColor: "rgba(0, 0, 0, 0.92)",
  color: "#ffffff",
  borderRadius: 6,
  padding: "6px 10px",
  fontSize: 14,
  lineHeight: 1.2,
  maxWidth: 240,
  boxShadow: "0 4px 10px rgba(0, 0, 0, 0.25)"
}
```

A tooltip arrow is optional and is not required for version one.

Expanded buttons must not show the tooltip by default.

# 27. Accessibility

Each control must use a native button.

Requirements:

* All buttons are reachable with Tab.
* Enter activates the focused button.
* Space activates the focused button.
* Disabled buttons use the native `disabled` attribute.
* Switch buttons use `aria-pressed`.
* Collapsed buttons use the full label as their accessible name.
* Icon-only buttons must have:

```tsx
aria-label={button.label}
```

* Expanded buttons may rely on their visible text as the accessible name.
* Tooltips supplement the accessible name and do not replace it.
* Focus must remain visually apparent in all states.
* Focus must remain visible in joined groups.
* Use a minimum 2-pixel focus outline.
* Focus indication must not rely only on a color change.
* Images must not create their own tab stop.
* Button labels should not be selectable during ordinary interaction.

---

# 28. Hover and Press Hit Area

The complete native button bounds must activate hover and press behavior, including transparent interactive margins.

Programmatically testable behavior:

* `pointerenter` on the transparent hit-area padding sets the button to hovered.
* `pointerdown` on the transparent hit-area padding sets the button to pressed.
* A valid release from that region activates the button.
* Pointer interaction with a child icon produces the same result as interaction with the surface.
* No child element stops propagation unnecessarily.
* In joined mode, adjacent hit areas must not overlap.

The minimum recommended total hit target is 40 by 40 pixels using the default `buttonHeightPx`.

The implementation is not required to automatically enlarge every custom configuration to a specific touch target, but the default configuration must meet this 40-pixel minimum.

# 29. Loading and Empty States

When:

```ts
parameters.state === "not-started"
```

or:

```ts
parameters.state === "loading"
```

render a Radix skeleton matching the approximate button-group dimensions.

Do not parse or render the final buttons until the parameters are loaded.

If the group contains no valid buttons, show:

```text
No valid buttons are configured.
```

If `buttonsJson` cannot be parsed, show:

```text
The button configuration is not valid JSON.
```
